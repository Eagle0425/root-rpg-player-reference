# 翻譯與內容品質流程

參考 [game-doc-template](https://github.com/wayne930242/game-doc-template) 的術語、翻譯決策、隔離草稿與分段檢查做法，依本專案的速查介面調整。

## 資料責任

| 資料 | 唯一用途 |
| --- | --- |
| `terms.json` | 原文術語、採用譯名、禁用異譯與決策來源 |
| `style-decisions.json` | 使用者已確定的翻譯與呈現要求 |
| `../reference.json` | 玩家規則正文與結構化數值 |
| `../gm-reference.json` | GM 專用正文、表格及書中案例 |
| `catalog.json` | 由正文產生的跨書目條目索引，不另存一份正文 |
| `reviews.json` | 綁定譯文版本的審查紀錄 |
| `quality-report.json` | 檢查結果及待審數量，不作完整翻譯率 |

不要直接編輯 `site/data.js` 或 `site/gm-data.js`，兩者由正文生成。不要將英文原文或原始 PDF 加入公開發布目錄。

## 每批工作順序

1. 依核心／擴充與書內頁碼定位來源，閱讀完整段落；遇到表格、多欄或不明文字，再看 PDF 圖像。
2. 讀取集中術語表及翻譯決策；新增譯名先記為候選，不自動冒充使用者核准。
3. 在獨立草稿中翻譯。原文條件、選項、數值、例外及書中案例不得省略；編者註另存 `editor_note`。
4. 將草稿整合到唯一正文資料；使用穩定 ID，保留原有收藏與深連結。
5. 執行 `node scripts/translation-quality.mjs --write`：檢查術語、來源、重複 ID、表格、核心／擴充分類與來源疑義。
6. 對照原書做語義審查，特別檢查誰選、何時付代價、成功是否仍達目標、閾值及修正。將審查類型、來源範圍與譯文雜湊記錄在 `reviews.json`。程式檢查通過不能取代這一步。
7. 執行 `node scripts/sync-data.mjs` 與 `node scripts/validate.mjs`；預覽桌機及手機，檢查搜尋、篩選、來源標示與連結。
8. 若正文影響 PDF 或角色卡，先記入跨成果檢查表，更新產製來源並重新生成；不能只改網站就宣稱所有輸出同步。

## 來源與狀態

條目索引以 `book`（core／exp）、`pages`（印刷頁碼）、`audience`（player／gm）、`category`、`pointer`（正文位置）、`sha256`（內容版本）管理。網址與分類可改，內容 ID 應保持穩定。

審查狀態分成 `recorded`（已有內容）、`source_checked`（來源比對）、`semantic_reviewed`（語義審查）。沒有有效審查紀錄的條目維持 `recorded`，即使舊文字標記寫著完整譯文，也不自動視為校對完成。

## 發布檢查

CI 會重新產生索引至記憶體，比對已提交的版本，再檢查正文與發布資料一致。這能阻擋過期索引與已知術語錯誤；不能保證沒有漏譯或誤譯。覆蓋率仍須依原書章節及段落人工核對，勿以有頁碼的條目數計算百分比。
